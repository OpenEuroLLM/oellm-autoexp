# Corroborated NCCL peer exclusion

`RestartAction.nccl_peer_scan` is opt-in (default false); `auto_restart_ckptreset_faultscan` enables it for its restart actions. After a faulty allocation is cancelled and leaves the queue, the monitor invokes `oellm_autoexp/monitor/nccl_peers.py` in a child process with a 60-second deadline, then runs the existing pre-command and refreshes exclusions. Cancellation and restart admission remain unchanged. Scanner timeout/failure is logged and recovery continues. This is post-failure attribution, not an additional monitor loop or a new trigger on a warning alone; the configured terminal-state, NCCL timeout and progress-stall rules still decide when to recover.

The scanner reads `nccl-HOST.log` sidecars one directory above the main `logs/slurm-JOB.log`. It accepts only `IBV_WC_RETRY_EXC_ERR(12)` warnings with a peer IP, a reporter matching its allocated host and filename, and a timestamp within the allocation's start/end window plus 120 seconds for teardown. Slurm `NodeAddr` must uniquely map that address to another node in the failed allocation. That peer must currently be `DOWN+NOT_RESPONDING`, with `LastBusyTime` within the attempt window. No DNS guess or exclusion of the reporting receiver is made. Missing, ambiguous, stale, healthy, bare CUDA-cleanup or unsupported evidence produces no exclusion. More than four corroborated peers requires review. Sidecars from other attempts are ignored by timestamps; use job-specific NCCL filenames/directories when available to avoid losing overwritten historical evidence.

Scheduler calls are each bounded to ten seconds, scanning is limited to 16 MiB per file and 128 MiB total, and the exclusion lock waits at most three seconds. The shared exclusion file must already exist. The scanner appends evidence to `nccl-peer-events.jsonl` beside the sidecars before appending new exclusions, preserves existing entries/comments, and skips already excluded nodes. The live `slurm.exclude_file` must point to the same list so rendering cannot override the hook's update with a stale snapshot. Generic users with another log layout can invoke the CLI from their existing pre-command with an explicit `--log-root`.

```bash
# Use an activated project Python. Omit --apply for read-only inspection.
python oellm_autoexp/monitor/nccl_peers.py --job 1725379 --log-root /path/to/training_core --exclude-file /path/to/exclusions.txt
python -m pytest -o addopts='' -p no:cacheprovider tests/monitor/test_nccl_peers.py tests/monitor/test_deferred_restart.py tests/monitor/test_restart_hooks.py
```

The regression fixture preserves the September 9, 2026 job 1725379 warning: receiver jpbo-022-09 reported retry exhaustion to 10.128.42.10, mapping to jpbo-071-42 with DOWN+NOT_RESPONDING and LastBusyTime coincident with job failure. Tests replay the actual warning and cover rejected evidence, bounded locking, missing accounting, missing audit/list, duplicate application, and a real autoexp cancel/defer/hook/render lifecycle with fake scheduler executables. Scanner timeout and failure still permit recovery after cancellation. No GPU fault was induced and no faulty node was deliberately allocated. Independent replay of the 512 retained sidecars found exactly the peer; the retained 1730171 CUDA-cleanup case found no peers. These results validate the software path, not a proven hardware root cause.
